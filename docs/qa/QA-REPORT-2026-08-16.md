The rework is in good shape. The economy loop — the heart of the game — is correct everywhere I could poke it, including the subtle cases (partial payments persist, pay plates don't collide with dawn coins, branch choice gates funding). The failures are all in **failure handling**: one corrupted save state bricks the Continue button forever with zero feedback, and any runtime exception in the frame loop silently kills the game.

## Bugs

### BUG-1 — Corrupted save permanently bricks Continue, with zero player feedback *(Severity: High)*

**Repro:**
1. Get a save whose snapshot contains a plot at a tier whose tier-def cannot resolve (demonstrated with a tower at tier 3, `branch: null` — see BUG-3 for how this state can arise).
2. Reload the page. The **📂 Continue** button appears.
3. Click Continue.

**Result:** `startGame()` is `async`; `Game._restore()` throws `TypeError: Cannot read properties of null (reading 'hp')` at `_addBuilding` (game.js:313, called from `_restore` game.js:115). The promise rejects unhandled. The player sees:
- a **"Loading…"** banner that never goes away,
- the menu still up behind it,
- no error message of any kind.

The save is never cleared or invalidated, so **Continue is dead forever** — every future visit shows the same broken button. The only recovery is manually clearing localStorage.

**Why it matters beyond the synthetic trigger:** every future save-format drift or partial write has this same blast radius. One bad field anywhere in the snapshot = permanently dead Continue, silently.

**Suggested fix (three small pieces):**
1. Wrap the Continue path in try/catch: on failure show *"This save is corrupted — starting fresh"*, clear `zillions_save`, return to menu.
2. In `_restore`, skip/repair plots whose `tierDef` resolves to null instead of passing null into `_addBuilding`.
3. Bump/validate the snapshot `v` on load; unknown versions get the same friendly-reset path.

### BUG-2 — Any exception in the frame loop silently hard-freezes the game *(Severity: Medium)*

**Repro:** cause any throw inside `frame()` (demonstrated via a building with `def: null` making `_updateTowers` throw; see BUG-3).

**Result:** `renderer.setAnimationLoop(() => this.frame())` has no error guard. After the throw, the render/sim loop never runs again: the game freezes in place — no error overlay, no prompt to reload, HUD stops updating, autosave stops. The player's only recourse is noticing and refreshing.

**Suggested fix:** wrap the `frame()` body in try/catch; on exception show a non-blocking "The city glitched — reload?" overlay with the message logged via `console.error`, and keep the menu reload path working. This turns every future unknown crash (including BUG-1-class save bugs that slip through) from "silent freeze" into "visible, recoverable".

### BUG-3 — `_construct` mutates plot state before validating the tier def *(Severity: Medium)*

**Where:** `game.js _construct()` — `plot.tier++` happens before `tierDef(plot, plot.tier)` is used; when the def resolves to null (branch tier with no branch chosen), the function throws **after** already incrementing the tier, leaving:
- the plot at max tier with `branch: null`,
- its building with `def: null` (assigned before the null-deref),
- `nextTier()` returning null → the plot is permanently un-upgradable,

and this poisoned state flows straight into `snapshot()` → BUG-1 on the next Continue.

**Normal-play gating:** the funding path in `_updatePlots` correctly refuses to fund a branch tier without a choice, and the branch UI requires standing at the plot — so the *direct* trigger is dev-API-only today. But the function is a state-corruption landmine (modding, future callers, save-restore ordering) and it is the root enabler of BUG-1.

**Suggested fix:** resolve the def first and only mutate on success:

```js
_construct(plot, free = false) {
  const def = this.tierDef(plot, plot.tier + 1);
  if (!def && !free) return;           // branch pending or bad tier — no-op
  plot.tier++;
  ...
}
```

### BUG-4 — `tutorialDone` is dead profile state *(Severity: Low)*

`_loadProfile()` initializes `tutorialDone: false` (main.js:248) but nothing ever reads or writes it; the tutorial is gated on `!profile.games` instead. Observed `tutorialDone: false` in a profile that had finished multiple runs. Harmless, but either wire it up (set on completion, gate on it) or delete the field.

## Code-review observations (not live-tested, from reading the rework)

1. **Co-op: any guest can ring the bell instantly.** `bell(p)` accepts any player index; a guest joining and pressing Space at day 1 forces night on everyone. Consider gating the bell to the host, or requiring ≥N seconds of daylight.
2. **Lobby hardening before growth** (lobby verified working live — these are abuse-resistance gaps, not breakage):
   - Chat `name` is client-supplied; anyone with the publishable key can impersonate another commander. Move identity/name authority to a Postgres RPC.
   - `addFriend` writes the reverse friendship row into the *other* player's table — a stranger can friend you silently if they know your code (which is semi-public). Confirm RLS actually restricts this, or restructure so only the friend-owner writes their rows.
   - No chat rate limit client-side; no TTL/cleanup on `zillions_chat` rows.
3. **`buildings.find` in the zombie-chew path** (`_moveZombie`) is O(horde × buildings) per attack tick. Fine at today's caps (perf sample below agrees); swap to an id→building Map if caps grow.
4. **Day phase has little to do** once coins are swept — creeps wake only within ~5 tiles of the city, so optional daytime objectives (clearable camps, coin caches) would fill the gap and feed the starved XP curve.
